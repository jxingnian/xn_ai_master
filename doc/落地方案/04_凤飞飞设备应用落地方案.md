# 第 4 阶段：凤飞飞设备应用落地方案

## 1. 文档信息

- 阶段编号：04
- 阶段名称：凤飞飞设备应用
- 文档版本：V1.0
- 制定日期：2026-10-30
- 应用编码：`feifei-device`
- 应用名称：凤飞飞设备
- 前置阶段：第 3 阶段 MQTT 应用

本阶段在平台中建设“凤飞飞设备”应用，完成设备接入、配对绑定、设备管理、在线状态面板、MQTT 业务消息处理和接入文档。MQTT 应用负责连接 EMQX、订阅和发布消息；凤飞飞设备应用负责设备身份、用户归属、业务状态和管理页面。

## 2. 建设目标

本阶段必须交付以下能力：

1. 提供设备状态查看面板，显示设备总数、在线数量、离线数量、未绑定数量和最近状态变化。
2. 提供设备增删改查、启用/停用、重命名、配置查看和设备状态查看。
3. 提供“连接设备”操作：后台生成一次性配对码，设备先通过 MQTT 上线，用户输入配对码后绑定当前用户。
4. 绑定过程必须校验配对码、设备在线状态、有效期、使用次数和当前用户权限。
5. 设备应用只能通过 MQTT 应用收发 MQTT 消息，不得自行创建 MQTT 客户端连接。
6. 提供完整的 API 接入、MQTT 配置、设备连接、配对绑定、故障排查和安全说明。
7. 所有配置和绑定结果持久化到数据库，服务重启后状态和设备归属不丢失。

## 3. 应用边界和依赖

```text
凤飞飞前端 ── HTTP API ── 凤飞飞设备应用 ── MQTT 应用 ── EMQX ── 凤飞飞设备
                                      │
                                      └── PostgreSQL
```

### 3.1 凤飞飞设备应用负责

- 设备登记、设备身份、产品型号和设备配置。
- 设备在线/离线状态和最后在线时间。
- 用户与设备的绑定关系。
- 配对码生成、校验、失效和审计。
- 设备状态、心跳、指令应答的业务解析。
- 设备管理页面和设备相关 REST API。

### 3.2 MQTT 应用负责

- 维护 `emqx-main` 等连接配置。
- 维护 MQTT 客户端、重连、订阅恢复和发布。
- 将 `status`、`telemetry`、`event`、`command_ack` 消息分发给 `device-manager` 消费者。
- 记录 MQTT 传输层结果。

设备应用禁止直接依赖 `mqtt` 客户端库，统一调用第 3 阶段提供的 `MqttService`。

    ├── 应用介绍
    ├── API 接入文档
    ├── MQTT 配置文档
    ├── 设备连接文档
    ├── 配对绑定流程
    ├── 消息主题和数据格式
    ├── 安全要求
    └── 故障排查

### 4.1 设备总览

页面必须显示：

| 指标 | 计算规则 |
|---|---|
| 设备总数 | 当前用户有权查看的有效设备数量 |
| 在线数量 | `last_seen_at` 在在线阈值内且状态为 `online` 的数量 |
| 离线数量 | 总数减在线数量 |
| 未绑定数量 | 已接入平台但没有有效用户绑定的数量 |
| 今日上线设备 | 当天至少收到一次有效心跳的设备数量 |

页面提供状态分布、最近上线设备、最近离线设备和最近告警事件。统计接口必须使用数据库聚合查询，不能由前端遍历全量设备计算。

### 4.2 设备管理

列表显示设备名称、设备 ID、产品型号、在线状态、最后在线时间、绑定用户、固件版本和更新时间。支持按名称、设备 ID、产品型号、在线状态和绑定状态查询。

操作包括查看详情、编辑名称和业务配置、启用、停用、连接设备、解绑、删除。删除前必须校验绑定关系；已绑定设备不能直接物理删除，先解绑并转为停用或由具备权限的管理员执行删除。

## 5. 设备状态模型

设备状态使用以下枚举：

```text
discovered  已发现，尚未绑定
online      在线
offline     离线
disabled    已停用
```

状态判定规则固定如下：

1. 收到设备有效 `status` 或 `heartbeat` 消息后，将设备更新为 `online`。
2. `last_seen_at + offlineThresholdSeconds < 当前时间` 时，设备状态变为 `offline`。
3. `disabled` 设备即使收到消息，也不能进入在线业务状态，消息记录为拒绝原因。
4. 默认 `offlineThresholdSeconds` 为 180 秒，后台支持按产品配置修改。
5. 心跳时间必须使用服务端接收时间 `received_at` 参与在线判断，设备时间只用于展示和诊断。
6. 重复消息按 `message_id` 去重，重复消息不得重复更新状态事件。

## 6. MQTT 设备接入规范

### 6.1 连接配置

后台 MQTT 应用使用第 3 阶段的 `emqx-main`：

```text
协议：mqtt（生产环境使用 mqtts）
主机：由 MQTT 应用连接配置保存
端口：1883（生产环境使用 TLS 端口）
客户端 ID：xn-platform-emqx-main
用户名：专用后台 MQTT 账号，不使用 admin
Keep Alive：60 秒
自动重连：启用
```

设备端使用 EMQX 分配的设备账号连接，禁止使用管理员账号。设备端必须保存设备唯一 ID、设备 MQTT 用户名、设备 MQTT 密码和服务器地址；密码不能写入设备上报 Payload。

### 6.2 主题

产品编码固定为 `xn_device`，主题格式为：

```text
xn/xn_device/{deviceId}/{messageType}
```

设备使用主题：

```text
发布：xn/xn_device/{deviceId}/status
发布：xn/xn_device/{deviceId}/telemetry
发布：xn/xn_device/{deviceId}/event
发布：xn/xn_device/{deviceId}/command_ack
订阅：xn/xn_device/{deviceId}/command
订阅：xn/xn_device/{deviceId}/ota
```

后台通过 MQTT 应用订阅：

```text
xn/xn_device/+/status
xn/xn_device/+/telemetry
xn/xn_device/+/event
xn/xn_device/+/command_ack
```

设备 ACL 只能访问自己的 `{deviceId}` 主题。后台 ACL 才能访问设备主题集合。

### 6.3 消息格式

```json
{
  "version": 1,
  "messageId": "01JDEVICE0001",
  "type": "heartbeat",
  "deviceId": "ESP32AABBCCDD",
  "timestamp": 1761800000000,
  "requestId": null,
  "data": {
    "firmwareVersion": "1.0.0",
    "ipAddress": "设备本地地址",
    "signal": -58
  }
}
```

服务端必须校验 `deviceId` 与主题中的设备 ID 一致、`messageId` 非空、`type` 属于允许集合、Payload 为合法 JSON，并限制 Payload 大小。校验失败的消息不得更新设备状态。

## 7. 设备连接与配对绑定流程

### 7.1 标准流程

```text
设备上电
  -> 设备连接 EMQX
  -> 设备发布 status/heartbeat（不携带配对码）
  -> MQTT 应用接收并分发
  -> 设备应用创建设备记录，状态为 discovered
  -> 后台用户点击“连接设备”
  -> 后台生成一次性配对码并通过 MQTT 临时下发给设备展示
  -> 用户读取设备当前展示的配对码并在后台输入
  -> 服务端校验配对码和设备在线状态
  -> 在事务中绑定 device_id 与当前 user_id
  -> 配对码立即失效
  -> 页面刷新为已绑定设备
```

### 7.2 配对码规则

1. 配对码只能由服务端使用密码学安全随机数生成，设备不得生成。
2. 设备只临时展示后台通过 MQTT 下发的配对码，不保存配对码；后台只保存 bcrypt 哈希，不保存明文。
3. 默认有效期 10 分钟，最多使用 1 次；过期、使用或主动取消后立即失效。
4. 同一设备同一时刻只允许一个有效配对码；重新生成或解绑会使旧码失效，再次绑定必须重新由后台生成。
5. 输入错误累计 5 次后锁定该配对码并写入审计日志。
6. 绑定必须在数据库事务中完成，并对设备绑定关系加唯一约束，防止并发绑定。
7. 用户只能绑定自己有权限的设备；管理员可按权限替其他用户绑定。

### 7.3 连接设备交互

设备管理页面点击“连接设备”后打开弹窗，输入配对码并提交。提交前页面显示设备 ID、设备名称和当前在线状态；服务端再次实时校验，不以页面显示结果作为授权依据。绑定成功后返回设备详情和绑定时间。

## 9. 后端 API 设计

所有接口使用现有 JWT Guard、权限 Guard 和统一错误格式。响应不得返回设备密钥、MQTT 密码或配对码哈希。

```text
GET    /api/feifei-devices/overview
GET    /api/feifei-devices
POST   /api/feifei-devices
GET    /api/feifei-devices/:id
PATCH  /api/feifei-devices/:id
POST   /api/feifei-devices/:id/enable
POST   /api/feifei-devices/:id/disable
DELETE /api/feifei-devices/:id

POST   /api/feifei-devices/:id/pairing-codes
POST   /api/feifei-devices/:id/pair
POST   /api/feifei-devices/:id/unbind
GET    /api/feifei-devices/:id/pairing-records

GET    /api/feifei-devices/:id/status-events
POST   /api/feifei-devices/:id/commands
GET    /api/feifei-devices/docs/:documentCode
```

### 9.1 生成配对码

```json
POST /api/feifei-devices/{id}/pairing-codes
{
  "expiresInSeconds": 600
}
```

响应只返回生成成功和过期时间，明文配对码通过 MQTT 临时发送给设备展示：

```json
{
  "success": true,
  "expiresAt": "2026-10-30T12:10:00.000Z"
}
```

### 9.2 提交配对码

```json
POST /api/feifei-devices/pair
{
  "pairingCode": "483921"
}
```

服务端必须按顺序完成：校验用户权限、锁定配对码、校验未过期和未使用、校验设备在线、校验设备未被其他用户绑定、写入绑定关系、标记配对码已使用、写审计日志。任一步失败都回滚事务。

### 9.3 设备状态指令

`POST /commands` 通过 MQTT 应用发布 `command` 消息，返回 `requestId`。HTTP 成功只表示消息已经交给 MQTT 应用；设备执行结果由 `command_ack` 关联 `requestId` 返回。

## 14. 验收标准

### 设备状态

- 设备首次上报合法状态后自动进入设备列表。
- 总览正确显示总数、在线数、离线数和未绑定数。
- 心跳超过 180 秒未收到时状态变为离线。
- 重复 `messageId` 不会重复生成状态事件。
- 停用设备收到消息后不会恢复为在线。

### 设备管理

- 支持设备增删改查、筛选、分页、启停和详情查看。
- 删除和解绑严格区分，删除不会绕过有效绑定关系。
- 不同用户只能看到授权范围内的设备。

### 配对绑定

- 设备必须先通过 MQTT 上线，后台才允许有效绑定。
- 配对码为 6 位数字、10 分钟有效且只能使用一次。
- 错误 5 次后配对码锁定。
- 并发提交同一配对码只允许一个绑定成功。
- 绑定成功后设备与当前用户关联，旧配对码立即失效。

### MQTT 和安全

- 设备应用不创建独立 MQTT 客户端，所有消息通过 MQTT 应用收发。
- 后台使用专用 MQTT 账号，设备账号只能访问自己的主题。
- 密码、设备密钥和配对码哈希不出现在接口响应和普通日志中。
- API 权限、审计日志、连接状态和消息错误均可追溯。

### 文档和部署

- 应用内可以查看 API 接入、MQTT 配置、设备连接、配对绑定和故障排查文档。
- 本地编译、测试通过后才执行部署。
- 所有部署和编译脚本位于项目对应的 `build` 目录，且适用于不同客户服务器配置。
